01 · Screens

Three destinations, nine rendered states

A single-activity app with three destinations: forecast (start), search, and day/{date}. The forecast screen is one vertical scroll — hero, 3-hour strip, readings ledger, 5-day list — so "today" and "week" live in the same scroll. Five days is the maximum available from OpenWeatherMap's free tier; the day list is aggregated client-side from 3-hour slots (§ Data mapping), and the row component accepts 5–7 entries.

04 · Behavior & states

Interaction rules and the full state matrix

Forecast screen

  • Source of truth: the screen observes selected city from DataStore — a nullable value. While it is null (first launch, nothing chosen yet) the screen shows the empty state (Frame F) prompting the user to pick a location; once set, it persists across launches. Changing city (from search or GPS) just writes to DataStore — the forecast screen reacts, no result-passing between destinations.
  • Load policy: emit cache immediately if present → fetch when cache is missing or older than 30 min, or when the screen resumes stale, or on pull-to-refresh (which always fetches).
  • Hero collapse: the hero block exits-until-collapsed with the scroll — fully expanded at rest, gone once the list takes over, at which point the pinned app-bar title switches from "Budapest" to "Budapest · 27°" (and back on return to top).
  • Day details: tapping any row in the five-day list — Today included — opens the day/{date} destination. The screen performs no fetch: it renders from the forecast held in the repository, and functions offline. Today's log lists only remaining slots; the free tier returns no past data. If the date rolls past midnight while backgrounded, the screen pops back to the dashboard.
  • GPS button: tap → coarse-location permission if not granted → fused location (balanced power) → OWM reverse geocode → write city to DataStore. Denied → snackbar "The city won't give you up. Name it yourself." with a Name it action. "Never ask again" → same snackbar, action opens app settings.
  • Search icon navigates to search; the title is a status line, not a control.

Search screen

  • Autofocus with keyboard up; query is debounced 300 ms, min 2 chars, limit 10, previous request cancelled.
  • Row tap → save city (+ prepend to recents, max 5, deduped) → return to the forecast screen.
  • Empty query → "Cold cases" header + stored rows; no matches → centered "No leads on 'xyz'."; geocoding error → inline "The search hit a wall." + "Run it again" text button.

Day details screen

  • Entry & exit: from any day row; back arrow and system back both return to the dashboard. App bar: back + "{Weekday} · {Mon D}".
  • Content, top to bottom: HeroBlock day-variant (day max, no feels-like) → the typed day log under "{Weekday}, step by step" → the details ledger → attribution. No hour strip here — that stays a dashboard device.
  • Day log rows: 48 dp — time · glyph · precip % · typed in-day marker (a typed + on the dot track at (t − day min) ⁄ day span) · temp. Today's log lists only the remaining slots.
  • No states of its own: renders from the repository forecast — no fetch, no loading state, no error state. Midnight rollover while backgrounded pops back to the dashboard.

Three OWM behaviors to account for: ① main.temp_min/max in /weather is a same-moment spatial spread, not today's range — H/L is derived from the aggregation below. ② wind is m/s even with units=metric. ③ all dt values are UTC; shift by the response's timezone offset before formatting labels, so a searched Tokyo shows Tokyo's clock.

Daily aggregation — data layer, unit-tested

  • Bucket each 3-h slot by local calendar date (dt + timezone offset).
  • Day min = min of main.temp_min; max = max of main.temp_max over the bucket. Today additionally folds in the current temp from /weather.
  • Day condition = the slot nearest 13:00 local, with the glyph forced to its day variant.
  • Day precip = max pop × 100, shown at ≥ 10%.
  • Render "Today" + following dates having ≥ 4 slots — normally exactly 5 rows; a thin trailing partial day is dropped.

API key & caching

The key lives in a git-ignored local.properties entry, reaches the network layer through build configuration, and is attached to every request as the appid query parameter by a network interceptor — it appears nowhere in source control.

  • Cache = the mapped domain model (+ fetchedAt, city), serialized with kotlinx.serialization into Preferences DataStore. One city cached at a time — matches "selected city" semantics. Room is the drop-in upgrade if you want per-city history.
  • Recents (max 5 cities) and selected city live in the same DataStore.
  • Staleness threshold 30 min; timestamps rendered as "The trail was warm at HH:mm".

StateCarriesRenders as

The screen renders from exactly one of these values — no side-channel flags outside the contract. Navigation contract: single activity, routes forecast (start), search, and day/{date}. City selection is never a navigation result: search persists the chosen city to app state and returns. The details route carries only a date and re-reads the cached forecast — no result passing anywhere, and everything survives process death.

Theme resolution: one fixed day/night pair (§ 02), switched by the system dark-mode flag — dynamic color is retired (decisions log). Typography is a single bundled family, Courier Prime, in the roles of § 02; ink, stroke, shape and grain values come straight from § 02 — that section is the single source of truth for core:designsystem.

07 · Accessibility & motion

The quality floor

  • Semantics: each day row is one merged element — "Friday: rain likely, 18 to 27 degrees"; each hour column "6 PM, 26 degrees, 10 percent chance of rain". Day rows announce their action ("Opens Friday details"); details log rows merge to one element each ("15:00, 26 degrees, 35 percent chance of rain"). Icon buttons get contentDescriptions ("Use current location", "Search for a city", "Back") — literal, not noir; decorative weather glyphs are null. The condition stamp doubles as the literal label for screen readers; the noir line and the typed glyphs are decorative — nothing ever reads "slash slash slash" aloud.
  • Contrast: hero text is onSurface on background. The eight stamp inks meet ≥ 4.5:1 against their own theme's background; the ≤ 5% grain shifts measured ratios by under 0.2, so all pairs remain above threshold. Precip info is glyph + color, never color alone.
  • Font scaling: everything in sp; hour columns get intrinsic-height head-room; test at 200%.
  • Targets: everything tappable ≥ 48 dp (see § 02 table).
  • Motion: loading is a single blinking block cursor (530 ms on, 530 ms off, hard steps — no fade) occupying the temperature slot, with static dot-leader placeholders below it at ~40% opacity; skeleton→content crossfade 250 ms; screen transitions default fade-through; banner 200 ms fade+expand. All decorative animation respects the system's "remove animations" setting. The grain is a static texture — nothing to disable; under reduced motion the cursor stops blinking and stays solid.
