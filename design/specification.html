01 · Screens

Three destinations

A single-activity app with three destinations: forecast (start), search, and day/{date}. The forecast screen is one vertical scroll — hero, hourly strip, readings ledger, seven-day list — placing today and the week in the same scroll. Open-Meteo returns seven complete days pre-aggregated in its daily block, so the list draws seven rows and no client-side aggregation exists (§ Data mapping).

04 · Behavior & states

Interaction rules and the full state matrix

Forecast screen

  • Source of truth: the screen observes a nullable selected city in persisted app state. Null (first launch, no selection) renders the empty state, Frame F. A set value persists across launches. Search and the location action write to that state; the forecast screen observes it. No result passing between destinations.
  • Load policy: emit cache immediately if present → fetch when the stored forecast is missing or older than one minute, when the screen resumes stale, or on pull-to-refresh (which always fetches).
  • Hero collapse: the hero block exits-until-collapsed with the scroll — fully expanded at rest, gone once the list takes over, at which point the pinned app-bar title switches from "Budapest" to "Budapest · 27°" (and back on return to top).
  • Day details: tapping any row in the five-day list — Today included — opens the day/{date} destination. Inside the one-minute age the screen performs no network call and renders from the store; past it it refetches and rewrites the store. The log is 3-hourly: eight slots at three-hour spacing across the day. If the date rolls past midnight while backgrounded, the screen pops back to the dashboard.
  • Location action: tap → request location permission if not granted → resolve position → reverse geocode through the platform geocoder → write the place to app state. Refusal renders the full-screen LocationRefused state (Frame J), carrying canAskAgain: while the platform still offers the prompt the action is Ask again; once it does not, the action opens system settings. Permission held but no position renders LocationUnavailable (Frame K) with a Try again action. The search screen carries the same distinction as an inline notice.
  • Search icon navigates to search; the title is a status line, not a control.

Search screen

  • Autofocus with keyboard up; query is debounced 300 ms, min 2 chars, limit 10, previous request cancelled.
  • Row tap → save the place (+ prepend to recents, max 15, deduped) → return to the forecast screen.
  • Empty query → "Cold cases" header + stored rows; no matches → centered "No leads on 'xyz'."; geocoding error → inline "The search hit a wall." + "Run it again" text button.

Day details screen

  • Entry & exit: from any day row; back arrow and system back both return to the dashboard. App bar: back + "{Weekday} · {Mon D}". States: loading, content, and unavailable when the date falls outside the seven days.
  • Content, top to bottom: HeroBlock day-variant (day max, no feels-like) → the typed day log under "{Weekday}, step by step" → the details ledger → attribution. No hour strip here — that stays a dashboard device.
  • Day log rows: 48 dp, gap 8 dp — time · glyph · precip % · typed in-day marker (a typed + on the dot track at (t − day min) ⁄ day span) · temp. Today's log lists only the remaining slots.
  • Reads through the same pipeline as the dashboard. Inside the one-minute age the repository answers from the store with no network call; past it the day refetches and rewrites the store, and because the store is keyed by coordinates the dashboard picks that up on return without a call of its own.

Open-Meteo → this UI

No API key: Open-Meteo's free tier requires none, so the repository runs without setup. Two hosts over one shared HTTP client; reverse geocoding is a platform call rather than a request.

Payload shape. Hourly and daily arrive as parallel arrays: time[3], temperature_2m[3] and weather_code[3] are three facts about one hour. The mapper zips them by index, reads only as far as the shortest column, and files each hour under its own local date. Times carry no offset (2026-08-09T15:15) and attach to the zone the response names, so a forecast keeps the clock of the place rather than the reader.

Two clocks

The hour strip and the freshness line run on the reader's clock; sunrise, sunset and the day log stay on the place's. A forecast for Tokyo read from Budapest shows Tokyo's sunrise and the reader's "in two hours".

Day and night come from is_day. Clear and partly cloudy take ink-night after dark; heavier weather keeps its own ink around the clock.

Storage

  • Key-value store, JSON under a handful of keys. Forecasts are keyed by coordinates: up to 15 are kept, evicted by insertion order.
  • The stored value is the raw response plus the place label and savedAt, so reading it back runs the same mapper as the live call.
  • Recents cap 15. Staleness threshold one minute.

Forecast screen — state contract

StateCarriesRenders as
Empty—Frame F; no place selected yet
Loading—Typed skeleton (Frame D); a place is selected, nothing stored yet
Contentcity · hero · hours · readings · days · isRefreshing + nullable offlineFrames A/B. The offline case is content carrying a notice, not a separate state

LocationRefusedcanAskAgain: BooleanFrame J; the flag decides between offering the prompt again and sending the reader to settings
LocationUnavailable—Frame K; permission held, no position. Separate because retrying can succeed

The screen renders from exactly one of these six values. Day details carries three (Loading, Content, Unavailable); search results carry four (Recents, Cities, NoResults, Error) plus a two-case location notice. Navigation contract: single activity, routes forecast (start), search, and day/{date}. City selection is never a navigation result: search persists the chosen city to app state and returns. The details route carries only a date and re-reads the cached forecast — no result passing anywhere, and everything survives process death.

Theme resolution: one fixed day/night pair (§ 02), switched by the system dark-mode flag — dynamic color is retired (decisions log). Typography is a single bundled family, Courier Prime, in the roles of § 02; ink, stroke, shape and grain values come straight from § 02 — that section is the single source of truth for core:designsystem.

07 · Accessibility & motion

The quality floor

  • Semantics: each day row is one merged element — "Friday: rain likely, 18 to 27 degrees"; each hour column "6 PM, 26 degrees, 10 percent chance of rain". Day rows announce their action ("Opens Friday details"); details log rows merge to one element each ("15:00, 26 degrees, 35 percent chance of rain"). Chrome glyphs carry contentDescriptions ("Use current location", "Search for a city", "Back", "Clear", "Recent", "Offline") — literal, not noir; decorative weather glyphs are null. The condition stamp doubles as the literal label for screen readers; the noir line and the typed glyphs are decorative — nothing ever reads "slash slash slash" aloud.
  • Contrast: hero text is onSurface on background. The eight stamp inks meet ≥ 4.5:1 against their own theme's background; the ≤ 5% grain shifts measured ratios by under 0.2, so all pairs remain above threshold. Precip info is glyph + color, never color alone.
  • Font scaling: everything in sp; hour columns get intrinsic-height head-room; test at 200%.
  • Targets: everything tappable ≥ 48 dp (see § 02 table).
  • Motion: loading is a single blinking block cursor (530 ms on, 530 ms off, hard steps — no fade) occupying the temperature slot, with static dot-leader placeholders below it at ~40% opacity; skeleton→content crossfade 250 ms; screen transitions default fade-through; banner 200 ms fade+expand. All decorative animation respects the system's "remove animations" setting. The grain is a static texture — nothing to disable; under reduced motion the cursor stops blinking and stays solid.
